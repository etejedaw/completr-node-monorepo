# Frontend

Arquitectura y convenciones de `apps/web`, la aplicación Angular que consume la API de `apps/api`. Las reglas generales de estilo, commits y post-edición están en [`conventions.md`](./conventions.md) y aplican a todas las apps.

## Stack

| Capa           | Tecnología                                                 |
| -------------- | ---------------------------------------------------------- |
| Framework      | Angular 22 (standalone, sin NgModule, zoneless)            |
| Lenguaje       | TypeScript 6.0                                             |
| Reactividad    | Signals                                                    |
| Formularios    | Signal Forms (`@angular/forms/signals`)                    |
| Estilos        | Tailwind CSS 4 + tokens por tema en `src/styles/themes/`   |
| Componentes UI | Design system propio en `shared/ui/` sobre `ng-primitives` |
| Iconos         | Material Icons                                             |
| PWA            | `@angular/service-worker` (`ngsw-config.json`)             |
| Testing        | Vitest + jsdom (`@angular/build:unit-test`)                |
| Build          | `@angular/build:application`                               |

## Conexión con el backend

| Config      | Valor                                                                         |
| ----------- | ----------------------------------------------------------------------------- |
| Base URL    | `apiUrl` en `src/environments/` (`http://localhost:3000` en desarrollo)       |
| Auth        | JWT Bearer en header (`authInterceptor`) + refresh token (`errorInterceptor`) |
| Token store | `localStorage` (`core/services/storage.ts`)                                   |

Las rutas `/share/*` (página de vista previa e imágenes del Rewind) se sirven bajo el dominio de la web, no el de la API. En producción el `location ^~ /share/` de `nginx.conf` hace proxy a la API; la URL interna sale de la variable de entorno `API_UPSTREAM` (con esquema, sin ruta; por defecto `https://api.completr.app`), que la imagen de nginx sustituye en la plantilla `/etc/nginx/templates/default.conf.template` al arrancar. En producción tiene que apuntar al contenedor interno de la API (`http://srv-captain--<app-de-la-api>:<puerto>`): con el valor por defecto el pedido vuelve a salir por Cloudflare, que reemplaza `cf-connecting-ip` por la IP del propio servidor, y todas las visitas a `/share/` comparten un solo cupo de rate limit. El proxy reenvía `X-Real-IP` tal como lo escribió el nginx de CapRover (`$http_x_real_ip`) en lugar de pisarlo, porque la API lo usa para decidir si confía en `cf-connecting-ip` (ver Rate limiting en [`../invariants.md`](../invariants.md)). En local `ng serve` usa `proxy.conf.json`, que manda `/share` a `http://localhost:3002`. `ngsw-config.json` excluye `/share/**` de `navigationUrls` para que el service worker no responda esos enlaces con el `index.html`.

Un service worker usa la CSP que venía con su script al instalarse, y el navegador solo lo reinstala si `ngsw-worker.js` cambia byte a byte. Angular genera ese archivo idéntico en cada build mientras no cambie su versión, así que un cambio en `security-headers.conf` no llegaría a los clientes que ya tienen el worker. Por eso el `postbuild` de `apps/web` corre `scripts/stamp-service-worker.mjs`, que agrega al final del worker `self.completrBuildFingerprint = "<hash>";`. El hash sale del worker, de `ngsw.json`, de `security-headers.conf` y de `nginx.conf`: cambia cuando cambia la app o los headers, y es estable si no cambia nada. `ngsw.json` no incluye el worker en su tabla de hashes, así que modificarlo después del build no rompe la verificación. Cuando el worker nuevo está listo, `app.ts` escucha `VERSION_READY` de `SwUpdate`, lo activa y recarga la página; revisa si hay actualización cada 5 minutos y cada vez que la ventana recupera el foco.

Al arrancar, `provideAppInitializer` intenta renovar el access token si está vencido, antes de resolver la primera ruta.

Dos páginas muestran contenido que no vive en este repo de Angular sino en la landing: What's new (`GET /changelog`) y Privacy (`GET /privacy`). La API hace de proxy con caché de 5 minutos y la página lo pide con `httpResource`, con esqueleto mientras carga y un estado de error con _Try again_. Al leer el recurso en la plantilla, comprueba `hasValue()` antes de `value()`: en estado de error `value()` lanza. Para cambiar esos textos no se toca `apps/web`; ver [`landing.md`](./landing.md).

│   │   └── utils/

## Convenciones Angular

- **Standalone components.** Cada componente declara sus `imports`.
- **Signals para el estado.** `signal` y `computed` para estado local y compartido; RxJS solo para HTTP y streams (debounce, polling).
- **`inject()`** en vez de inyección por constructor.
- **Signal inputs y outputs** (`input()`, `input.required()`, `output()`).
- **`ChangeDetectionStrategy.OnPush`** en los componentes.
- **Interceptors y guards funcionales** (`HttpInterceptorFn`, `CanActivateFn`), no clases.
- **Lazy loading** con `loadComponent` en `app.routes.ts` y `PreloadAllModules`.
- **Signal Forms** para formularios.
- **`readonly`** en inputs, outputs y señales que no se reasignan; **`protected`** para lo que solo usa la plantilla.
- **Sin `ngClass` ni `ngStyle`**: se usan los bindings `[class]`, `[class.x]` y `[style.x]`. La única excepción es `layout.html`, que mantiene un `[ngClass]` junto a `routerLinkActive`.
- **Plantilla inline** en componentes chicos y `templateUrl` en los grandes. Una página que crece se parte en hijos dentro de `features/<feature>/components/` (por ejemplo, My Games tiene 8).
- **Imports solo de lo usado**, sin `CommonModule`. El build avisa con `NG8113` cuando sobra un import.
- **`httpResource`**: se lee con `hasValue()` antes de `value()`, porque `value()` lanza cuando el recurso está en error.
- **Espacios entre elementos inline**: Prettier junta los elementos inline y se come los espacios entre ellos. En una frase con enlaces intercalados se usa un separador explícito `{{ " " }}` (ver `feed-activity-item.html`).

```typescript
@Component({
	selector: "app-game-card",
	imports: [RouterLink],
	templateUrl: "./game-card.html",
	changeDetection: ChangeDetectionStrategy.OnPush
})
export class GameCard {
	readonly game = input.required<Game>();
	readonly gameClicked = output<Game>();
}
```

## Patrones clave

- **El backend calcula todo.** Ratios, estadísticas y derivados vienen de la API; el frontend solo renderiza.
- **La lógica HTTP va en services.** Los componentes no inyectan `HttpClient`.
- **Componentes de página vs. componentes reutilizables.** Las páginas orquestan estado y HTTP; `shared/` solo recibe inputs y emite outputs.
- **Sin carpetas globales por tipo.** Fuera de `core/` y `shared/`, todo vive dentro de su feature.
- **Si falta un dato, se amplía la API.** Cuando un diseño necesita algo que el endpoint no envía (portadas, conteos, `role`), se agrega en la API con un cambio aditivo y se actualiza `docs/api/`. El frontend no lo arma con llamadas extra.
- **Lógica compartida con funciones `inject*`.** El comportamiento que repiten varias páginas (buscar juegos, agregar a My Games, seguir usuarios, scroll spy) va en una función `injectX()` dentro de la feature dueña. No se copia de página en página.

## Tests

Los specs usan Vitest con jsdom a través de `@angular/build:unit-test`. Cada spec vive junto al archivo que prueba (`*.spec.ts`) y `describe`, `it`, `expect` y `vi` son globales.

- **Entorno común.** `src/test-environment.ts` (opción `setupFiles` del target `test` en `angular.json`) completa lo que jsdom no implementa y la app necesita: `Element.prototype.getAnimations`, que `ng-primitives` llama al cerrar toasts, diálogos y menús. Ningún spec lo define ni lo borra por su cuenta: un toast que se cierra después de que su spec terminó (su temporizador sigue vivo) caería en otro archivo y rompería la corrida según el orden en que se ejecuten.
- **Deterministas.** Un spec da el mismo resultado en cada corrida sin cambios en el código. No depende de cuánto tarda la máquina: el reloj se fija con `vi.spyOn(performance, "now").mockReturnValue(...)` cuando el componente mide tiempo (el margen de apertura de `UiDialog` y `UiBottomSheet`), y para probar un debounce las teclas se disparan en el mismo turno (`fireEvent.input` en un bucle) en vez de confiar en que `user.type` sea más rápido que el debounce. Las esperas fijas solo sirven para comprobar que algo no ocurre.

| Comando                                     | Qué hace                                 |
| ------------------------------------------- | ---------------------------------------- |
| `npm run test -w apps/web`                  | Corre los specs en modo watch            |
| `npm run test -w apps/web -- --watch=false` | Corre los specs una vez (CI, pre-commit) |

### Patrones

- **Services HTTP**: `provideHttpClient()` + `provideHttpClientTesting()` y `HttpTestingController`. Cada test comprueba URL (con `environment.apiUrl`), método, params o body y el mapeo de la respuesta, y `afterEach` llama a `httpTesting.verify()`. Si el service arma los params con `buildHttpParams`, se busca la petición con `expectOne(req => req.url === ...)` y se inspeccionan los `params`.
- **Guards e interceptores funcionales**: los guards se ejecutan con `TestBed.runInInjectionContext` y un `AuthService` falso (`useValue`). Para el resultado se acepta `boolean`, `UrlTree` u `Observable` (`lastValueFrom`) y las redirecciones se comparan con `router.serializeUrl`. Los interceptores se prueban a través de `HttpClient` con `provideHttpClient(withInterceptors([...]))`.
- **Estado de módulo**: `errorInterceptor` guarda `isRefreshing` a nivel de módulo, así que todo test que dispare un 401 debe terminar el refresh (`next` + `complete`, o `error`) para no contaminar al siguiente.
- **Componentes**: `TestBed.createComponent`, inputs con `fixture.componentRef.setInput` y `fixture.detectChanges()` después de cada interacción (la app es zoneless). Se prueba lo que se renderiza y los outputs emitidos, no los métodos internos. Los componentes con `routerLink` necesitan `provideRouter([])`.
- **Dobles**: servicios con estado o efectos (`AuthService`, `ToastService`, `ViewportService`, `FavoritesService`) se reemplazan con `{ provide: X, useValue: {...} }` y `vi.fn()`. `StorageService` se prueba con el `localStorage` de jsdom, limpiándolo en `beforeEach`.
- **APIs que jsdom no trae** (`ResizeObserver`, `CSS.escape`): se stubean con `vi.stubGlobal` en `beforeEach` y se restauran con `vi.unstubAllGlobals()` en `afterEach`.
- **Bugs conocidos**: se dejan como `it.todo("...")` con la descripción del comportamiento esperado; no se corrigen dentro del PR de tests.
- Los specs no llevan comentarios: el nombre del `it` en inglés describe el comportamiento.

### Tests de interacción

Los `<pantalla>.interaction.spec.ts` simulan lo que hace un usuario en una pantalla entera (login, My Games, Lists, ficha de juego, Up Next, Want to Get): hacen clic, escriben, abren diálogos y comprueban lo que se ve después de cada paso. Usan `@testing-library/angular` (`render`, `screen`, `within`, `waitFor`), `@testing-library/user-event` y los matchers de `@testing-library/jest-dom`, que cada spec activa con `import "@testing-library/jest-dom/vitest";` en la primera línea (no hay setup global).

- **Render**: `render(Pantalla, { providers, routes })` del entry principal de `@testing-library/angular`, que funciona con la app zoneless: tras cada evento de `user-event` y en cada `findBy*` / `waitFor` corre la detección de cambios de los fixtures montados. Si el recorrido cruza pantallas (crear una lista y aterrizar en su detalle, login y redirección), se renderiza un host con `<router-outlet />` y las rutas reales, con `initialRoute`.
- **Consultas**: por rol y nombre accesible (`getByRole("button", { name: "Move Celeste up" })`, `getByRole("dialog", { name: "Edit run" })`, `getByLabelText("Notes")`), acotadas con `within(...)` cuando el mismo control se repite por fila o tarjeta. Las pantallas renderizan a la vez la versión de escritorio y la de mobile (jsdom no aplica Tailwind), así que un control puede aparecer dos veces: se acota al contenedor (`within(screen.getByRole("navigation", { name: "Filter by status" }))`) o se toma el primero. El input de `ui-search-bar` toma su nombre accesible de `ariaLabel` (por defecto, el placeholder sin los puntos suspensivos finales): se busca con `getByRole("textbox", { name })`. Los botones de acción de `app-game-cover-card` incluyen el título del juego en su nombre ("Remove Hades from Want to Get"); el overlay de escritorio y la barra táctil se alternan con `display: none`, así que solo uno llega a la tecnología de asistencia (jsdom muestra ambos). La tarjeta de `app-backlog-entry-card` se nombra con título y estado ("Hollow Knight, Not Started") y el resto de su contenido la describe con `aria-describedby`.
- **API simulada con estado**: `provideHttpClient()` + `provideHttpClientTesting()` y una función `answer(req)` que responde cada petición como la API (lista, filtra por `status` o `search`, aplica `PATCH`, `PUT` y `DELETE` sobre un arreglo local) y lanza `Unexpected request` para cualquier URL que no conozca. `answerPending()` responde en rondas todo lo pendiente (`httpTesting.match(() => true)`), porque una respuesta dispara otras peticiones. `untilVisible(assertion)` envuelve `waitFor` y responde lo pendiente en cada intento: cubre los `debounceTime` de las búsquedas sin fake timers. `afterEach` responde lo que quede y llama a `httpTesting.verify()`.
- **Aserciones sobre la API**: además de lo visible, cada recorrido comprueba el body que llegó al servidor simulado (los `PATCH`, el orden que manda `PUT /items` o `PUT /queue`, los `DELETE`), guardado en arreglos que se vacían en `beforeEach`.
- **Sesión**: para que la pantalla sepa quién es el dueño (`isOwner`, `isLoggedIn`) se usa el `AuthService` real y se llama a `loadUser()` después del render; el `GET /users/me` lo responde la API simulada.
- **Diálogos**: `DialogService` (ng-primitives) los monta en `document.body`; se buscan con `screen.findByRole("dialog", { name })`. Cuando se cierran desaparecen del DOM.
- **Popovers y menús**: el contenido de un overlay de ng-primitives se renderiza de forma reactiva, así que los atributos que ponen sus primitivos (`aria-multiselectable`, `aria-activedescendant`) aparecen un ciclo después de abrirlo. Tras abrirlo, `await fixture.whenStable()` antes de leer esos atributos o de navegar con el teclado.
- **Toasts con Undo**: se monta `<app-toast-container />` en el host y se registra el fixture como componente raíz con `TestBed.inject(ApplicationRef).components.push(fixture.componentRef)`, porque `NgpToastManager` busca el `ViewContainerRef` en `applicationRef.components[0]`. El Undo se prueba con el botón _Undo_ y el commit con _Dismiss_, sin esperar los 5 segundos de `UNDO_WINDOW_MS`.
- **`@defer (on viewport)`**: en jsdom el disparador de viewport de Angular no llega a observar el placeholder aunque se stubee `IntersectionObserver`, así que un recorrido no puede depender de que un bloque diferido se renderice. Lo que el recorrido necesita ver se carga con `appInView` (que sí usa el stub) o se prueba en el spec del componente (`rewind.interaction.spec.ts` deja diferidas solo las portadas por mes y "More Rewinds").
- **Reordenar**: el drag & drop de CDK no se simula; se usan los botones "Move up/down" y "Move to top", que son la alternativa accesible que exige la app.
- **APIs que jsdom no trae** en estos recorridos: `matchMedia` (`PointerService`, `ViewportService`) e `IntersectionObserver` se stubean con `vi.stubGlobal`; `Element.prototype.getAnimations` (salida de los toasts) se define en `beforeEach` como `() => []` y se borra con `Reflect.deleteProperty` en `afterEach`.

## Nombres

- Archivos en `kebab-case`. Componentes y el service principal de una feature sin sufijo (`game-card.ts`, `backlog.ts`); guards e interceptors con sufijo (`auth.guard.ts`, `auth.interceptor.ts`). Cuando una feature tiene varios services, van en `services/` con sufijo `.service.ts`.
- Clases, interfaces y tipos en `PascalCase` (`GameCard`, `BacklogEntry`).
- Los tipos compartidos entre features (el contrato con la API) viven en `core/models/`. El resto de las `interface` y de los `type` que describen un objeto (también una unión de objetos) van en un `<archivo>.model.ts` junto al archivo que los usa (`rewind-tally.ts` → `rewind-tally.model.ts`, `audit.service.ts` → `audit.model.ts`), nunca dentro de un componente, service, guard, directiva o util; las uniones de literales que esos tipos necesitan viajan con ellos. Se quedan donde están los tipos derivados de una constante o función (`(typeof X)[number]`, `ReturnType<typeof injectX>`), las firmas de función y los tipos locales de un spec.
- Selectores con prefijo `app-` o `ui-` (lo valida ESLint). Los componentes de `shared/ui/` que extienden un elemento nativo usan selector de atributo (`<button uiButton>`).
- URLs en `kebab-case` (`/game-shelf`, `/saved-views`).

## Diseño visual

### Temas y tokens

- Tema oscuro. Los tokens (`--color-*`, `--font-*`, `--radius-card`) se registran en `@theme` de Tailwind dentro de `src/styles.css`, y cada tema los redefine en su propio archivo `src/styles/themes/<id>.css` (bloque `:root[data-theme="<id>"]`, importado desde `styles.css`). Las clases usan siempre los tokens (`bg-surface`, `text-brand`), nunca hex sueltos.
- `ThemeService` (`core/services/theme.ts`) aplica el tema con `data-theme` en `<html>`, lo guarda en `localStorage` y en el usuario (campo `theme` de la API). El catálogo vive en `THEME_CATALOG` del frontend y en `apps/api/src/users/constants/theme.constants.ts`; un tema nuevo necesita su archivo en `src/styles/themes/`, su `@import` en `styles.css` y una entrada en ambos catálogos.
- Temas: `refined-dark` (por defecto, **Refined Dark**: grafito casi negro con violeta), `midnight-cyan` y `twilight-arcade`.
- Significado de los tokens de color:

| Token                              | Uso                                                                                                                                                                          |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `brand`, `brand-hover`             | Acentos y texto de marca. Debe cumplir 4.5:1 sobre `canvas`, `surface` y `surface-hover`                                                                                     |
| `brand-solid`, `brand-solid-hover` | Superficies rellenas con texto blanco (botón primario, insignias). 4.5:1 con el blanco                                                                                       |
| `brand-subtle`, `brand-glow`       | Fondos translúcidos y halos                                                                                                                                                  |
| `rating`                           | Estrellas y notas (igual a `brand`)                                                                                                                                          |
| `playing`                          | Estado Playing; distinto de `brand` en cada tema                                                                                                                             |
| `premium`                          | Dorado reservado a Premium: insignias, listones, contadores de tope y `toast.premium`                                                                                        |
| `admin`                            | Platino reservado al rol Admin: insignia de rol (`bg-admin-metal text-admin`), anillo y halo del avatar del admin, y sección Admin del menú; no se usa en ninguna otra parte |
| `platinum`                         | Trofeo de platino de un juego (`PlatinumTrophy` y título de la ficha); cian hielo distinto de `admin`, `premium`, `playing` y `brand` en cada tema                           |
| `warning`                          | Naranja de advertencias. El amarillo no se usa fuera de Premium                                                                                                              |
| `success`, `danger`, `info`        | Completado, destructivo/abandonado e información                                                                                                                             |
| `nav-*`                            | Color de identidad de cada sección del menú; `nav-admin` apunta a `admin`                                                                                                    |

- Texto secundario y atenuado (`fg-secondary`, `fg-muted`) también cumplen 4.5:1 sobre los tres fondos, y en cada tema la jerarquía `fg` > `fg-secondary` > `fg-muted` debe seguir siendo visible. Al tocar un tema, recalcular los contrastes.
- Sombras: `shadow-popover` (menús y selectores flotantes), `shadow-table` (tablas con marco), `shadow-sheet` (hoja inferior de `UiBottomSheet` y de `UiDialog` en mobile), `shadow-dock` (barras ancladas al borde inferior), `shadow-card` (tarjeta de `BacklogEntryCard` en hover y en edición), `shadow-toast` (toasts) `shadow-ring-brand` (anillo de marca de 3px: foco del buscador global y de `UiSearchBar`, y el formulario resaltado de reseña y de lista) y `shadow-tone-icon` (halo del ícono con tono en el encabezado de `UiDialog`, `UiDrawer` y `UiBottomSheet`, en `currentColor`) se registran como `--shadow-*` en `@theme`. El texto blanco sobre una imagen lleva `drop-shadow-hero` (título de un héroe: juego, Browse, perfil, Settings → Profile) o `drop-shadow-cover` (título sobre la portada de `ListCard` y `FranchiseCard`), registrados como `--drop-shadow-*`. Las sombras son negras con alfa y no varían por tema, así que los archivos de `styles/themes/` no las redefinen. No se escriben sombras con `shadow-[...]` repetidas en las plantillas: si una se usa en más de un sitio, pasa a token.
- Superficies y bordes: `canvas`, `sidebar`, `surface`, `surface-hover`, `input-bg`, `line` y `line-hover`. Un hover sobre una fila usa `hover:bg-surface-hover`. Nunca se usa blanco o negro con alfa (`bg-white/[0.03]`), porque no se adapta a los temas.
- La raíz mide **14px** (`html { font-size: 14px }`), así que las clases en rem de Tailwind salen un 12,5% más chicas: `h-11` mide 38,5px y `gap-2` mide 7px. Los tamaños mínimos (44px táctiles, separaciones de 8px) se escriben en px: `min-h-[44px]`, `gap-[8px]`.

### Tipografía

- **Chakra Petch** (pesos 500, 600 y 700) para títulos y cifras destacadas (`font-display`) y **Manrope** (variable, 200 a 800) para el texto (`font-sans`).
- Servidas localmente desde `public/fonts/` (subconjuntos latin y latin-ext, `font-display: swap`), declaradas en `chakra-petch.css` y `manrope.css`. No se cargan fuentes de terceros. Ambas tienen licencia SIL Open Font License 1.1; su texto va junto a los archivos (`*-OFL.txt`) y debe acompañar a cualquier fuente que se agregue.
- Columnas de datos con `tabular-nums`.

### Shell

- `layout/` es el shell autenticado: barra lateral (o riel colapsado) y topbar con búsqueda global en escritorio; topbar, barra inferior de pestañas y hoja "More" en mobile. `guest-shell` es la versión para visitantes.
- El scroll vive en `main` (`.page-scroller`, contenedor de consultas `page`); cada página va dentro de `.page-shell`. No se pone `isolate` en `<main>`, porque rompe el apilamiento de las hojas inferiores.
- Medidas del shell como variables CSS en `styles.css`: `--topbar-height`, `--tabbar-height`, `--page-max-width`, `--page-pad-x`, `--page-pad-y` y `--page-pad-top`. Las barras fijas se pegan con `top-[var(--topbar-height)]`.
- Escritorio: barra lateral que se colapsa a riel (se guarda en `localStorage`, y en tablet de 768 a 1023px es siempre riel) y búsqueda global inline con el atajo `/`. Mobile: barra inferior de 5 pestañas (Feed, My Games, Up Next, Browse, More) y búsqueda en overlay (`MobileSearchOverlay`, `layout/mobile-search-overlay`: diálogo modal movido a `body` con `injectBodyPortal({ restoreFocus: true })`, foco atrapado con `UiFocusTrap`, Escape o Cancel lo cierran una sola vez y el foco vuelve al botón de búsqueda). El rol del usuario en el sidebar y en la hoja More es `ui-badge` con `badge.tone`; Settings y Sign out de la hoja son `uiButton` `secondary` y `danger`.
- Toda la configuración de los toasts (posición, separación del borde, gap, cuántos se ven a la vez y duraciones) vive en `TOAST_CONFIG`, en `core/services/toast.ts`. En mobile se separan del borde inferior para quedar sobre la barra de pestañas. Se ven como máximo `maxToasts` a la vez: los que ng-primitives marca con `data-visible="false"` se ocultan. Un toast con el mismo variant, título y mensaje que uno ya mostrado lo reemplaza en vez de apilarse; los de Undo (`pending`) nunca se fusionan. Hay un solo `ToastContainer`, montado en `layout`. `ng-primitives/toast` no está en el bundle inicial: `ToastService` lo importa con `import()` dinámico, lo precarga en idle tras el arranque y aplica ahí la configuración de posición (no hay `provideToastConfig` en `app.config.ts`). Los toasts pedidos antes de que termine la carga se encolan y se muestran en orden; si el import falla, el siguiente toast lo reintenta. El loader es el token `TOAST_LIBRARY_LOADER`, que los specs reemplazan para controlar la carga.

### Utilidades globales (`src/styles.css`)

| Utilidad                                  | Qué hace                                                                                                          |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Variante `tap:`                           | Aplica en pantallas de menos de 640px **o** con puntero táctil. Se usa para tamaños táctiles (`tap:min-h-[44px]`) |
| `pointer-coarse:`                         | Solo para mostrar u ocultar según el puntero, nunca para tamaños                                                  |
| `.tap-area`                               | Amplía el área táctil a 44px con un `::after` invisible, sin cambiar el tamaño visual                             |
| `.bleed`, `.bleed-inner`, `.bleed-top`    | Llevan un bloque a todo el ancho del contenedor de página manteniendo el contenido alineado con el resto          |
| `.poster-grid`, `.poster-grid-actionable` | Grilla de portadas; la variante con acciones usa columnas más anchas en mobile                                    |
| `.bleed-scroll-snap`                      | Alinea el scroll horizontal de carruseles con el margen de la página                                              |

- `.tap-area` dentro de un contenedor con `overflow-x-auto` necesita padding vertical táctil en el contenedor (`pointer-coarse:py-[8px]`) para que el área no se recorte. Tampoco se usa en enlaces de líneas contiguas, porque las áreas invisibles se solapan: en ese caso se da `tap:min-h-[44px]` a cada enlace (ver `AttributionFooter`).
- El design system (`styles/ui.css`) ya da 44px bajo 768px o con puntero táctil a `.ui-button`, `.ui-icon-button`, `.ui-tab` y al área del interruptor (`.ui-switch__track::after`). `.ui-input` mide 44px en todos los anchos salvo `size="sm"`. Los elementos propios usan `tap:` o `.tap-area`.

### Patrones de composición

- **Encabezado de página**: `LibraryHero` es el único dueño de la separación entre su contenido y la línea inferior. Las vistas no ponen `mb-*` ni `pb-*` en `[heroSubtitle]`, `[heroActions]` ni en el contenido proyectado, y el contenedor de acciones se oculta vacío (`empty:hidden`). Si el contenido proyectado necesita padding táctil por estar en un `overflow-x-auto`, se compensa con un margen negativo igual (ver `user-backlog.html`).
- **Hero de detalle** (juego, perfil): ocupa todo el ancho con `bleed bleed-top`. Lleva una imagen difuminada y otra nítida con máscara, un degradado hacia `canvas`, el contenido alineado abajo en `bleed-inner` y `fetchpriority="high"` en la imagen principal. Lo de más abajo usa `loading="lazy"`.
- **Eyebrow + título**: un eyebrow en mayúsculas con `tracking` amplio y color de marca, y debajo el título en `font-display font-bold tracking-tight`. El eyebrow de marca es `uiEyebrow tone="brand"` (`tone="premium"` en Premium), nunca clases escritas a mano. Las etiquetas de formulario usan `uiFieldLabel` (texto normal) y los títulos de sección dentro de formularios o listas, `uiEyebrow` con el tono por defecto.
- **Barra de herramientas fija**: `LibraryToolbar` (`sticky` bajo la topbar, fondo `canvas` translúcido con `backdrop-blur`).
- **Hero o barra**: el lugar de un control lo decide si cambia datos o solo la vista. En `[heroActions]` van las acciones que crean o cambian datos (Add game, Create list, Track saga, New view, Reorder, Surprise me): como máximo una primaria y una secundaria, y el resto en un `ActionMenu` `⋯` (`placement="hero"`, `iconOnly`), como el detalle de una lista propia. Si varias acciones del mismo tipo compiten por ser la primaria, van juntas en un `ActionMenu` con `variant="primary"` (Run job en Admin → Jobs). Refresh solo recarga la vista: va al final de la barra si la vista tiene una y, si no, como botón de ícono en el hero (Admin → Jobs, Promotions y Reports), para no crear una barra vacía. El "Add game" de admin en Browse va arriba de la barra, junto al título o bajo el carrusel. La ficha de un juego sigue la misma regla en `GameLibraryActions`: la acción primaria es My Games (o la última run), la secundaria Favorite, y Up Next, Want to Get, My Shelf y Lists van en un `ActionMenu` "More library actions" (`size="lg"`) cuyos ítems muestran dónde ya está el juego ("In Up Next", "On My Shelf", "In 2 lists") con el color de la sección (`iconClass`). En Feed, el selector "Show" va en `LibraryToolbar`, alineado con el ancho del feed. Debajo del título van las pestañas de alcance (estados, plataformas, Created / Following). En la barra va lo que solo cambia cómo se ve la lista, siempre en este orden: búsqueda → vista guardada → filtros → orden → modo de vista → Export. Un control queda en la misma zona en escritorio y en mobile; en mobile se adapta (fila completa, hoja inferior), no se muda.
- **Listas minimalistas** (Feed, Up Next, actividad): filas con `divide-y divide-line`, miniatura de portada, una frase con los nombres resaltados y la hora a la derecha. Sin tarjetas.
- **Estados completos**: el esqueleto tiene la forma real del contenido (nunca "Loading..."). El vacío lleva ícono, título, texto y una acción útil. El error y el privado explican qué pasó y ofrecen una salida.
- **Carruseles con rotación**: se pausan con hover o foco, tienen botón de pausa, no rotan con `prefers-reduced-motion` y usan `aria-live="off"` mientras rotan.
- **Datos con color**: nunca solo color; siempre etiqueta y número.
- **Navegación con enlaces reales** (`routerLink`), no botones con `router.navigate`. Los botones quedan para acciones.

### Búsqueda contextual

- **Una sola barra.** En el shell autenticado no conviven dos buscadores: la barra superior es a la vez la búsqueda global y el filtro de la página. Una página que filtra su lista monta `app-page-search` (`shared/components/page-search`) donde antes iba `ui-search-bar`, con `scopeLabel` (el nombre de la sección tal como lo ve el usuario: "My Games", "Up Next", "etejedaw's games"), `placeholder`, `[value]` y `(valueChange)`. La página sigue siendo dueña de su estado (señal, debounce, query params); el componente solo reenvía.
- **Registro.** `Layout` provee `PageSearchScope` (`core/services/page-search-scope.ts`, no es `root`). Dentro del `Layout`, `app-page-search` registra su alcance (`label`, `placeholder`, `ariaLabel`, `value`, `setValue`), no dibuja nada y se desregistra al destruirse, solo si sigue siendo el alcance activo. Hay un alcance a la vez y el último registrado gana. Fuera del `Layout` (visitante en `GuestShell`, specs con `TestBed`) dibuja el `ui-search-bar` de siempre.
- **Escritorio.** Con alcance, `GlobalSearch` muestra el chip "In <label>" dentro del campo, el placeholder de la página y el nombre accesible "Filter <label>"; lo escrito llama a `setValue` en vivo y el desplegable dice "Filtering <label>" y ofrece "Search "<q>" in all of Completr". Quitar el chip (su ✕, Backspace con el campo vacío o esa acción) limpia el filtro de la página y pasa el texto a la búsqueda global (Games, Players, Lists; Enter → Browse); el foco queda en el campo. En modo global, si la página tiene alcance, el desplegable ofrece "Filter <label> by "<q>"", que vuelve a poner el chip con ese texto. Al cambiar de página el chip pasa al alcance nuevo (o desaparece) y el campo toma el valor de esa página. Escape primero limpia el texto y después sale del campo. Un `role="status"` anuncia el modo ("Filtering My Games" / "Searching all of Completr").
- **Mobile.** Con alcance, la topbar reemplaza el logo y el botón de búsqueda por la misma `GlobalSearch` en variante `compact`: campo de 44px con el chip, sin desplegable, para que la lista siga visible mientras se filtra. Las tres variantes (`inline` en escritorio, `compact` en la topbar mobile y `overlay` en `MobileSearchOverlay`) comparten la lógica de chip, teclado y búsqueda; solo cambia cómo se dibujan. Quitar el chip limpia el filtro, emite `searchedEverywhere` y el `Layout` abre `MobileSearchOverlay` con el texto (`initialQuery`); desde el overlay, "Filter <label> by "<q>"" lo cierra y vuelve a filtrar la página. Sin alcance, el botón de búsqueda abre el overlay como siempre.
- **Cuándo no.** Los buscadores dentro de un diálogo, una hoja o un paso de "agregar" (Add to Up Next, el selector de juegos, `GameSearchStep`) no filtran la página: siguen con `ui-search-bar`. Las páginas sin lista que filtrar (Feed, ficha de un juego) no montan `app-page-search` y la barra superior se comporta como búsqueda global.

### Fechas y errores de campo

- **Fechas.** Se eligen con `UiDatePicker`, nunca con `<input type="date">` ni `type="datetime-local"`: el nativo muestra el formato y el calendario del sistema ("dd/mm/aaaa" según el idioma) y no sigue el tema. El disparador muestra "Nov 3, 2026" o "Nov 3, 2026, 14:30" (reloj de 24 horas) y su nombre accesible es "Label: fecha" (o "Label: placeholder"). Un valor ilegible o vacío muestra el `placeholder` ("Select date" o "Select date and time" por defecto).
- **Calendario.** Usa `ng-primitives/date-picker` con el adaptador nativo, semana desde el domingo. Al abrir, el foco va al día elegido, o a hoy, o al primer día permitido si hoy queda fuera de rango. Flechas, Home / End y PageUp / PageDown (mes anterior o siguiente) mueven el foco; Enter o Espacio eligen; Escape cierra sin cambiar el valor y devuelve el foco al disparador. El pie tiene _Today_ (deshabilitado si hoy está fuera de rango) y _Clear_ si el campo es `clearable`.
- **Fecha y hora.** En `mode="datetime"` elegir un día no cierra: conserva la hora y _Done_ cierra. Horas y minutos tienen botones de 44px (los minutos saltan de 5 en 5) y un `spinbutton` con flechas (de a 1), PageUp / PageDown (6 horas o 10 minutos) y Home / End. Si todavía no hay día, la hora queda como borrador hasta elegirlo.
- **Rangos.** `minDate` y `maxDate` van en el mismo formato que el valor, deshabilitan los días fuera de rango y en `datetime` acotan también la hora. No se llaman `min` / `max` porque Angular no deja enlazarlos junto a `[formField]` (NG8022). Un par From / To pasa cada extremo como `maxDate` / `minDate` del otro, así nunca queda From > To (filtros Started y Finished de My Games).
- **Formularios.** Con `[formField]` implementa `FormValueControl<string>` (`value`, `invalid`, `touched`, `disabled`) y emite `touch` al cerrar o limpiar; el borde `danger` y `aria-invalid` aparecen solo con el campo tocado. Fuera de un formulario se usa `[(value)]` o `[value]` / `(valueChange)` y `[invalid]` marca el error directamente. La etiqueta visible va afuera con `<label uiFieldLabel [for]>` apuntando a `triggerId`, sin `uiFormField` ni `uiLabel`, que reescriben el `for` hacia un control de ng-primitives.
- **Errores de campo.** Todo error bajo un campo es `UiFieldError`; no se arma a mano con un `<p>`. Se enlaza por `aria-describedby` (con `describedBy` en `UiDatePicker` y `OptionPicker`) y el campo lleva `aria-invalid`. Dentro de `uiFormField` con `uiInput` basta `<ui-field-error uiDescription>`, que se registra solo. No tiene rol por defecto para que el lector no lo anuncie dos veces (al aparecer y al volver al campo); `announce` le pone `role="alert"` para un error que llega mientras el foco está en otro lado (la búsqueda de RAWG del editor de juegos). Los errores de una acción que no pertenecen a un campo (activar un regalo, Surprise me) siguen como texto con `role="alert"`.
- **Specs.** Para elegir una fecha como un usuario, `pickCalendarDate(user, trigger, "YYYY-MM-DD")` de `shared/ui/date-picker/ui-date-picker.testing.ts` abre el calendario, navega hasta el mes y hace clic en el día. Los specs que necesitan una fecha con hora o un valor que la UI no puede producir (vacío en un campo obligatorio) fijan `value` en la instancia con `getDebugNode(trigger.closest("ui-date-picker"))` y emiten `touch`. Un mensaje de error se busca con `selector: "ui-field-error span"` o `.closest("ui-field-error")`, porque el texto va en un `span` junto al ícono.

### Patrones de interacción

- Mobile primero: toda acción se puede hacer con el dedo y nada depende solo del hover. En filas y tarjetas, escritorio muestra íconos (32px, 44px con `tap:`) y mobile un `ActionMenu` `iconOnly` `variant="ghost"` con `icon="more_vert"` (oculto desde `sm:`), que abre la hoja con las acciones grandes y con texto (`QueueRow`, `SavedViewCard`, `ListItemRow`, `TagRow` y las filas de Admin).
- Mostrar u ocultar según **tamaño de pantalla y puntero a la vez** (`max-sm:` y `pointer-coarse:`), nunca solo por puntero: un navegador angosto con mouse tiene que funcionar igual que un celular.
- En mobile se **adapta** el mismo formato de la vista, no se reemplaza por otro: una grilla de portadas sigue siendo grilla, con una barra de acciones bajo cada portada. Si el diseño de escritorio ya funciona, se conserva y solo se adapta mobile (caso `GameCoverCard`: botones flotantes en escritorio, barra en mobile y táctil).
- Cambiar el estado de una entrada del backlog se hace con `BacklogStatusPicker`, nunca con un menú propio. Elegir una opción se hace con `OptionPicker`, que abre un menú en escritorio y una hoja inferior en mobile. Todas las opciones aparecen debajo del disparador o en la hoja, nunca sobre el contenido. Orden de apilamiento: `UiBottomSheet` en `z-[1000]` (una hoja abierta desde otra queda encima) y el menú de `OptionPicker` en `z-[1010]`.
- Reordenar siempre ofrece una alternativa al arrastre (flechas o "Move up/down"), y el arrastre solo empieza desde el asa (`cdkDragHandle`).
- **Selección masiva** en las tablas Hardcore propias (My Games, My Shelf, Platinums): la página crea `injectRowSelection` sobre las filas visibles, pasa la selección a la tabla (input `selection`; sin él, o con `readonly` / sin `selectable`, no hay casillas), monta `BulkActionBar` solo en la vista Hardcore y limpia la selección al cambiar de vista. La selección es solo con la casilla; el clic en la fila sigue abriendo el editor y los controles por fila siguen activos. Los predicados de elegibilidad son funciones puras compartidas (`shared/utils/backlog-eligibility.ts`: `canChangeStatus`, `canRate`, `canQuickRate`, `canAddToQueue`, `uniqueGameIds`), los mismos que usan la tabla y la tarjeta del Diary. Favoritos se calcula por juego (`gameId` deduplicado): Favorite si alguno no es favorito, Unfavorite si todos lo son, y el otro en "More". Cambiar status y poner nota abren diálogos reducidos (`BulkStatusDialog` con `BacklogStatusPicker` y una sola fecha, hoy por defecto; `BulkRatingDialog` con `StarRating`) que avisan de las filas omitidas y de las notas que se reemplazan; Favorite, Up Next y privacidad son inmediatos; borrar es con Undo (`injectBulkRemoval`). My Games orquesta todo en `injectBacklogBulkActions` (`features/backlog/backlog-bulk-actions.ts`). Cada service tiene un `bulk(action, body)` tipado que llama a `POST .../bulk?action=...` y devuelve `data` (`BulkResult` de `core/models/bulk.model.ts`); `FavoritesService.bulk` actualiza `favoriteIds` de forma optimista, lo revierte si falla y se queda con los `succeeded`.
- Las acciones destructivas reversibles (quitar de una colección) usan `toast.pending` con _Undo_. La ventana es de 5 segundos para toda la app (`UNDO_WINDOW_MS` en `core/services/toast.ts`) y no se configura por pantalla. Las irreversibles (borrar un tag o una lista, cerrar la sesión de los otros dispositivos en Settings → Security) y dejar de seguir a alguien piden confirmación con un `UiDialog` `tone="danger"`, nunca con una confirmación en línea.
- Los topes del plan free (HTTP 402) los avisa `errorInterceptor` con `toast.premium` y el texto de `core/utils/plan-limit-message.ts`. `toast.premium` se llama solo desde ahí y desde `UiPremiumBadge`; las pantallas no crean sus propios toasts Premium.
- El Rewind tiene su paleta de identidad con tokens existentes (`features/rewind/rewind-tone.ts`): cada bloque recibe `[style.--tone]="toneVar(tone)"` y usa `TONE_SOLID_CLASS` (fondo del tono con todo el texto en `text-canvas`, porque el secundario mezclado no llega a 4.5:1 sobre `brand` y `danger`) o `TONE_TINT_CLASS` (22% del tono sobre `surface`, con `TONE_TINT_SECONDARY_CLASS` para el texto secundario: `fg-secondary` no cumple 4.5:1 sobre el teñido en `midnight-cyan`).
- La página `/user/:u/rewind/:year` es la única bilingüe de la app: se muestra en `rewind.language` (`en` o `es`) para todos los que la ven, con `lang` en el contenedor. Los textos viven en `REWIND_COPY` (`features/rewind/rewind-copy.ts`), tipado como `Record<RewindLanguage, RewindCopy>` para que una clave que falte en un idioma no compile; meses, fechas y números salen de `Intl` con el locale del idioma (`es`: `313,3`, `Marzo`, `4 mar`). Cada componente de la página recibe `language` como input opcional con `"en"` por defecto, así las vistas que los reutilizan fuera de la página siguen en inglés. Los estados de error usan el último idioma visto del mismo usuario y, si no hay ninguno, inglés. Un 404 `REWIND_NOT_GENERATED` (solo lo recibe el dueño) muestra "This Rewind hasn't been generated yet" con enlace al perfil. Inmediatamente después del hero está `#rewind-owner-panel-slot`, el lugar del panel del dueño, y `RewindDetail.replaceRewind(rewind)` reemplaza el `Rewind` mostrado sin volver a pedirlo (ignora uno de otro año o de otro usuario).
- El dorado `premium` del Rewind se reserva al marco de las secciones Premium (`REWIND_PREMIUM_FRAME_CLASS`); el resto de la paleta del Rewind no lo usa.
- El movimiento del Rewind se apaga entero con `prefers-reduced-motion` (`canAnimateRewind` en `rewind-motion.ts`, variantes `motion-safe:`): el revelado por sección (`appRewindReveal`, una vez, 420 ms, solo `opacity` y `translate`), el odómetro, la entrada de la persona (`animate.enter` con `uiFadeUp`), el conteo del tally, el abanico del spotlight y el zoom del arte al pasar el mouse. Nada queda en bucle.
- Un `Blob` que ya está en memoria (la imagen del Rewind) se descarga con `ExportService.saveFile(blob, fileName)`, el mismo `<a download>` temporal que usan las exportaciones.
- Las descargas de archivos van por `ExportService` (`core/services/export.ts`): pide el archivo con `observe: "response"`, `responseType: "blob"` y el formato en el header `Accept` (`text/csv` o `application/json`, sin query param `format`), toma el nombre de `Content-Disposition` (`filename*` antes que `filename`, con `completr-<recurso>-YYYY-MM-DD.<ext>` de respaldo) y lo descarga con `URL.createObjectURL` y un `<a download>` temporal, revocando la URL al terminar. Con `responseType: "blob"` el cuerpo de un error también llega como `Blob`: `errorInterceptor` lo lee y lo parsea como JSON (o lo deja como texto) antes de decidir el toast, así que el 402 `EXPORT_FORMAT_PREMIUM` muestra `toast.premium` como cualquier otro tope. `ExportActions` solo muestra un toast de error para los status que el interceptor no avisa. Un adjunto que no es una colección (la copia de datos personales del usuario o la que baja el admin) usa `ExportService.downloadAttachment(url, fallbackName)`, que hace lo mismo con la URL y el nombre de respaldo que se le pasen. Los status que avisa el interceptor (402, 409, 422, 429) se consultan con `isToastedByErrorInterceptor(status)` (`core/utils/toasted-error-statuses.ts`) para no repetir el toast.
- Los errores del admin sobre juegos, géneros y plataformas se traducen en `core/utils/admin-error-message.ts` (`adminErrorMessage(error)`, código `type` de la API → texto, `null` si no lo conoce). `errorInterceptor` lo usa para el toast de los 409, así que las acciones sueltas no repiten ese toast; el resto de los códigos los muestra la pantalla donde ocurre la acción: inline con `role="alert"` en formularios (`saveError` del editor de juegos) y toast en acciones sueltas (desactivar y borrar). Los valores de scores y duraciones se validan en el formulario antes de enviar, y los PUT masivos suprimen el toast de validación para dejar el error inline.
- Las solicitudes de datos personales (copia y borrado de la cuenta) tienen dos vistas. El usuario las pide en Ajustes > Your data (`features/settings/settings-data`): un botón por tipo, deshabilitado con la insignia "Pending · due <fecha>" mientras haya una pendiente de ese tipo, el borrado con un `UiDialog` `danger` de confirmación y el historial con estado, fechas, motivo del rechazo y "Download" mientras no venza `downloadableUntil`. El admin las procesa en `AdminDataRequests` (`app-admin-data-requests`, embebido en Admin > Users bajo las invitaciones): cola filtrada por estado con `SegmentedControl` (pendientes por defecto, el orden lo da la API), días restantes con `daysRemainingBadge` (`warning` con 7 días o menos, `danger` el día del vencimiento o pasado), Complete y Reject (`AdminDataRequestRejectDialog`, motivo obligatorio). Completar un borrado y el "Delete account" de cada fila de usuario (oculto para cuentas admin) piden escribir el username en `AdminAccountDeletionDialog`; las acciones de fila viven en `injectAdminUserDataActions` (`features/admin/admin-users/admin-user-data-actions.ts`). Tipo, estado y descarga disponible o vencida salen de `shared/utils/data-request-display.ts`, y los códigos de error (`DATA_REQUEST_*`, `USER_DELETE_FORBIDDEN`, `USER_NOT_FOUND`) se traducen en `DATA_REQUEST_ERROR_MESSAGES` (`core/utils/data-request-error-message.ts`), que `adminErrorMessage` incluye: los 409 los avisa el interceptor y los 404 y 410 la pantalla, que además recarga la lista.
- En los formularios del admin, un error del servidor (resumen o mensaje bajo un campo) se oculta en cuanto el usuario cambia el valor que lo produjo, sin esperar al siguiente envío: al fallar se guarda una foto de los valores enviados y un `computed` compara contra ella (`visibleCreateFieldErrors` en `admin-users`, `visibleInviteError`, `visibleError` del modal de sagas). Si el usuario vuelve al valor que falló, el error reaparece. Los errores de validación de Split y Compilation en el editor de juegos se limpian al editar cualquier fila.
- El dorado (`premium`) marca el premium completo efectivo, ya venga del rol o de una concesión temporal; el admin conserva el platino (`admin`). Las superficies que muestran un usuario pintan el anillo de `UiAvatar` con `avatarRing(role, hasPremium)` (`core/utils/premium.ts`). Un regalo individual no cambia el anillo.
- Las insignias salen de `elevatedRoleBadge(role, hasPremium)` en `core/utils/role-badge.ts`, con tokens. Premium temporal muestra Premium sin cambiar el rol; Mod y Admin conservan su insignia real y para `user` sin premium completo devuelve `null`.
- `AuthService.isPremium` se deriva de `user.premiumAccess.active` de `GET /users/me`, no se vuelve a calcular desde el rol. `AuthService.hasPremiumFeature(feature)` responde `true` con premium completo o si `user.premiumFeatures` incluye la feature (regalos individuales); las vistas que dependen de una feature concreta lo consultan a ella, no a `isPremium`.
- Los regalos premium se canjean con `GiftOfferCard` (`shared/components/gift-offer-card`, selector `app-gift-offer-card`), una card dentro de la sección de la feature, nunca un modal. Recibe `feature` (una `PremiumFeature` o `"*"` para el premium completo) y `variant` (`card` o `compact`), y emite `claimed` con la oferta activada y `expired` cuando un regalo activo vence con la vista abierta. Elige la oferta de esa feature con `selectGiftOffer` (`gift-offer-selection.ts`): primero una `active`, después una `available`, desempate por el `availableUntil` más tardío y luego por `code`. Solo renderiza `available` (título y descripción por feature de `GIFT_OFFER_COPY` en `gift-offer-copy.ts`, "Available until <fecha y hora>", que también es hasta cuándo dura el acceso, y el botón "Activate gift") y `active` (una línea discreta "Gift active until <fecha>"). Con `used`, `expired`, `not-eligible`, sin oferta, mientras carga o si el listado falla no renderiza nada. Un temporizador la oculta al llegar la fecha de fin con la vista abierta. Angular no decide elegibilidad ni duración: lo dice la API.
- `GiftOffersService.listOffers()` comparte una sola petición de `GET /users/me/gift-offers` entre todas las cards de la vista (`shareReplay`). La caché se descarta en cada `NavigationStart`, después de cualquier canje (exitoso o fallido) y cuando la petición falla. Las secciones que comparten un shell (Settings) piden el listado una vez.
- Al canjear, la card se protege del doble clic y muestra el error inline con reintento. Si la respuesta del canje no trae la oferta `active` (el admin terminó la promoción entre el listado y el canje) o el canje responde 404, 409 o 410, recarga el listado en vez de marcarla activa. Tras cualquier canje `active` recarga el usuario (`auth.loadUser()`) antes de emitir `claimed`, y también cuando vence un regalo activo, antes de emitir `expired`, para que `premiumFeatures` quede al día. Si esa recarga falla, se ignora: el acceso ya se concedió o ya terminó en la API.
- Dónde va cada regalo: `export.json` en `ExportActions` y, en el detalle de una lista propia, junto al menú `⋯` de las acciones del hero (con el mismo `injectExportDownload`, así el canje desbloquea JSON en ese menú), `lists.unlimited` en la vista propia de Listas (entre el aviso de listas congeladas y "Your lists"; al canjear recarga las listas para que `frozen` venga de la API) `rewind.premium` en el perfil propio, debajo de `ProfileRewindSpotlight` (solo si `isSelf()`; al canjear recarga los años del Rewind para que el diálogo de generación reciba el `premiumAccess` nuevo) y `"*"` arriba del contenido del shell de Settings. Exportación y Listas solo la montan si el usuario no tiene premium completo; el perfil y Settings la montan siempre para el dueño, porque la API responde `not-eligible` a quien ya tiene el acceso y quien lo tiene por un regalo ve ahí "Gift active until". En la barra de exportación la card compacta puede bajar a su propia línea en pantallas angostas (`ExportActions` usa `flex-wrap` y solo es `shrink-0` desde `sm`).
- Admin → Users tiene una acción Premium access separada de Edit user. `AdminPremiumAccess` y `PremiumAccessAdminService` gestionan premium temporal y features individuales con estados de carga, error y confirmación de revocación; el rol permanente se sigue editando solo en Edit user.
- `styles/ui.css` no está en una capa de cascada, así que sus reglas ganan a las utilidades de Tailwind: para cambiar `display`, ancho, alto, borde o fondo de un `uiButton` / `uiIconButton` hace falta el modificador `!` (p. ej. `sm:!hidden`).
- `uiButton` tiene ocho variantes: `primary`, `secondary`, `ghost`, `danger`, `premium`, `glass`, `link` y `link-danger`. `link` y `link-danger` son el botón con aspecto de enlace de texto (acciones dentro de una frase o de una línea de metadatos: "Add to My Games", "Report missing", "Read more"): sin padding, alto ni borde, texto de marca (`link-danger`, rojo), tamaño de fuente heredado del contexto (el `size` no les afecta), subrayado y `brand-hover` al pasar el cursor, contorno de foco como el resto y área táctil de 44px con un `::after` como `.tap-area` (ya no hace falta añadir `tap-area`). Un color propio del texto (el del estado en `ListItemRow`) va en un `<span data-link-label>` hijo, porque `ui.css` gana a `text-*` sobre el propio botón; con `data-link-label` el subrayado del hover pasa del botón a ese `span` y sale en su color. `glass` es el botón secundario sobre un héroe (fondo `surface` al 70% con `backdrop-filter`): reemplaza el override `!bg-surface/70 backdrop-blur` sobre `secondary`. `active` (`data-active`) pinta el estado activo de marca en `secondary`, `ghost` y `glass` (Filters, Stats). `danger` usa `color-mix` sobre `--color-danger`, así que sigue al tema. `uiIconButton` existe también como `a[uiIconButton]` para enlaces de ícono (Settings, What's new) y tiene `shape` `rounded` (por defecto) o `circle` y `variant` `plain` (por defecto) o `glass`, el botón de ícono sobre un héroe con el mismo fondo, borde y `backdrop-filter` que el `glass` de `uiButton` (flechas y pausa del carrusel de Browse, Share del perfil); con `aria-disabled="true"` queda atenuado y sin hover pero enfocable (botón de cerrar de un `UiDialog` no descartable). Los botones X de `UiDialog`, `UiDrawer`, `UiBottomSheet` y los toasts son `uiIconButton` `circle`. `uiIconButton` tiene `size` `xs` (20px, para ícono en línea dentro de una etiqueta o un chip: el botón de información de los campos del modal de backlog, la X de `MoodTagsInput`) con área táctil de 44px por `::after` en vez de `min-width`/`min-height`, y `tone` `neutral` (por defecto), `accent` y `danger`, que solo cambian el hover (`ActivityDeleteButton` usa `danger`). `premium` es el botón dorado de las acciones exclusivas de Premium (texto `premium`, fondo y borde `premium` al 10% y 25% con `color-mix`, 18% y 45% en hover, contorno de foco dorado) y se usa solo detrás de `*appPremiumOnly`, en acciones que dependen de una feature premium (el JSON de `ExportActions`) y en el botón de canje de `GiftOfferCard`.
- `ui-skeleton` es `block` y sus variantes `rect` y `circle` ocupan el alto del host: el tamaño se da en el host (`class="h-16 w-24 rounded-md"`).

### Proceso de diseño y verificación

- Cada decisión de UI, por chica que sea, se respalda con las guías de UX de `.claude/skills/ui-ux-pro-max` (`python3 .claude/skills/ui-ux-pro-max/scripts/search.py "<tema>" --domain ux`) y con la documentación actual de Angular, Tailwind y ng-primitives, no con lo que uno recuerda.
- Un cambio visual se verifica en tres casos: escritorio con mouse (1440×900), navegador angosto con mouse (390px) y celular táctil emulado (390×844). En cada uno se revisa que no haya objetivos táctiles de menos de 44px, desbordamiento horizontal ni errores de consola.
- Si una vista pública reutiliza la propia, el cambio en un componente compartido llega solo a las dos, pero la estructura de página puede seguir duplicada: al cambiar una, se revisan ambas.
- El login de la API admite 5 intentos por minuto (ver `invariants.md`). Los scripts de prueba inician sesión una sola vez y recorren los viewports en la misma sesión.
